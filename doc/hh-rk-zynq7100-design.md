## 1. Purpose

Bitstreams for the XC7Z100's programmable logic, built from Vivado batch Tcl —
no block design and no checked-in project; a `project` argument generates one
for the GUI. Each design is a directory with
`build.tcl`, `rtl/` and `xdc/`; the PS7 configuration is shared with the Linux
side (`../linux/board/ps7_config.tcl`), so there is one source of truth for
MIO, DDR and clocks.

| Design | What it is | Status |
|---|---|---|
| [`board/`](../pl/board) | Everything on PL pins: the 1 GB of PL DDR3 behind its MIG on M_AXI_GP0, the register file, LED8, the fan, LED1–4/KEY1–4 and all 34 J8 pins over EMIO, three I2C buses, the PL Ethernet port (GEM1 over EMIO through a GMII-to-RGMII core), five frequency counters (four oscillators and the camera's byte clock), three BIST engines (two into PS DRAM, one into the PL DDR3), HDMI out, HDMI in through a VDMA on S_AXI_HP0, the camera through a MIPI CSI-2 receiver and a second VDMA on S_AXI_HP3 (both VDMAs, the receiver and the register file behind an AXI-Lite crossbar on M_AXI_GP1), and the SFP cages with a PRBS exerciser on their transceivers | ✅ Built and run on hardware |
| [`ddr/`](../pl/ddr) | The same PL DDR3 and BIST engines, without the video, camera, Ethernet or transceiver logic: the minimal design for bringing a MIG up, where a failure has one possible cause | ✅ Calibrated and verified on hardware |

Both designs also carry `fan_ctrl.v` (the fan's PWM output stage and its
tachometer, on bank 11) and `emio_pads.v` (the board's I2C pins, handed to the
PS as EMIO GPIOs). See "The fan" and "I2C" below.

⚠ **The EMIO assembly is duplicated between the two top levels**, so a change
to one has to be made to the other and then actually loaded — building is not
enough to show the second copy agrees. After any EMIO change, reload `ddr/` and
read it back:

```
ID=0x5A710002  STATUS=0x3
EMIO bits[13:10]=0b0100 with led3 set, bits[17:14]=0b1111 (no key pressed)
fan1_input 1039 rpm, die 37.4 °C, fabric fallback not engaged
0x4000_0000 / 0x4000_0004 / 0x4FFF_FFF0 written and read back intact
```

⚠ The two tops also name their clock and reset differently: the full design uses
`clk`/`rstn`, `ddr` uses `fclk_clk0`/`ps_rstn`. Verilog invents a one-bit net
for an undeclared identifier rather than complaining, so a block pasted across
with `.rstn(rstn)` sits in permanent reset in a bitstream that meets timing and
runs. `pl/sim/run.sh` elaborates with `-Wimplicit`, which names the line.

## 2. Fan controller

The fan header J10 is on **PL** pins — `FAN_PWM` W21 and `FAN_TACH` Y21, bank
11 — so nothing can drive the fan until the PL is configured. What the PL
holds is only the pin end of it: `fan_ctrl.v` inverts the PWM and counts the
tachometer. The PWM itself is generated by the **PS**, by TTC1 channel 0,
reaching the fabric through EMIO, so Linux drives the fan with the mainline
`pwm-cadence` and `pwm-fan` drivers and it turns up under hwmon like any other
fan. See "Die temperature and the fan" in [the Linux guide](linux-guide.md).

TTC1, with its waveform outputs on EMIO, is enabled in the shared PS7
configuration. **It does not change the PS init**: the generated
`ps7_init_gpl.c`, `ps7_init_gpl.h` and `ps7_init.tcl` are byte-identical with
and without it, so SPL and U-Boot do not depend on it.

<a id="the-pin-is-inverted-and-that-makes-the-quiet-state-the-wrong-one"></a>
<a id="21-the-pin-is-inverted-and-that-makes-the-quiet-state-the-wrong-one"></a>
### 2.1 PWM polarity

NPN Q7 pulls the fan's PWM line low when W21 is high, and a 4-wire fan pulls
its own PWM input up, so **fan speed follows the time W21 spends LOW**. Passing
the TTC waveform straight out would make `pwm1 = 255` stop the fan, so
`fan_ctrl.v` inverts it — and inverting alone would mean that any time the PS
stops driving TTC1 (Linux not up yet, crashed, or a kernel without `pwm-fan`)
the pin sits high and the fan is held off by the one part of the system that is
certainly still running.

So `fan_ctrl.v` watches `pwm_in` for edges and, seeing none for 100 ms, drives
the pin low: **full speed, decided in the fabric, with nothing running on the
CPU**. The same idea as LED8's heartbeat. 100% duty also stops the edges and
also lands on full speed, which is what it asked for; 0% duty is the case the
fallback deliberately overrides, and software that really wants the fan
stopped sets `FAN_CTRL[1]`.

<a id="-with-no-bitstream-at-all-the-fan-is-off--not-on"></a>
<a id="22--with-no-bitstream-at-all-the-fan-is-off--not-on"></a>
### 2.2 Fan state before configuration

This is the opposite of what the inversion suggests, and it is a property of
the board, not of the design: **PUDC_B (A8) is strapped low through 1K**, so
the internal pull-ups are enabled during configuration, W21 is pulled HIGH, and
Q7 holds the fan's PWM line down. An unconfigured XC7Z100 therefore sits there
with its fan stopped.

Measured the board otherwise idle:

| State | Die temperature |
|---|---|
| `board/` loaded, `pwm1` = 255 | **38.4 °C**, and 33–34 °C after a few minutes |
| `board/` loaded, fan held off with `FAN_CTRL[1]` | 38.3 °C rising to **40.2 °C** over three minutes, still climbing |
| No bitstream loaded, fan therefore off | **46.5 – 47.0 °C** |

⚠ Take the last row as an upper bound: the reading carries heat stored from a
long preceding run of the `ddr/` design. What it shows is the direction and
rough size — **the fan is worth something like 8 °C**, and an unconfigured
FPGA does not have one. The thermal time constant is minutes, so a reading
taken soon after a change is somewhere on a curve.

Nothing in the PL can change that, so how long the part sits without a fan is
decided by whatever loads the bitstream. U-Boot's PREBOOT loads it before
Linux starts for exactly this reason, and `../linux/board/S15fpga` does so if
U-Boot did not.

<a id="registers"></a>
### 2.3 Registers

`FAN_STATUS` and `FAN_CTRL` are the last two words of the shared register file
(`0x18` and `0x1C` from its base; `0x8010_0018` and `0x8010_001C` in `board/`,
`0x8000_0018` and `0x8000_001C` in `ddr/`).

| Register | Bits | Meaning |
|---|---|---|
| `FAN_STATUS` RO | `[15:0]` | tachometer pulses in the last whole second |
| | `[16]` | the tachometer input, live |
| | `[17]` | the PWM waveform arriving from TTC1, live |
| | `[18]` | the fabric fallback is forcing the fan on |
| | `[19]` | `force_off` is holding the fan off |
| `FAN_CTRL` RW | `[0]` | disable that fallback |
| | `[1]` | `force_off`: hold the fan off, whatever the waveform does |

The same tachometer, synchronized, also leaves the PL on **EMIO GPIO 0**
(Zynq GPIO 54), where Linux's `pwm-fan` counts its edges on an interrupt and
publishes `fan1_input` in rpm. So the speed is measured twice, independently:
once in the fabric and once in the kernel, off the same wire. When a fan's
pulses per revolution is a guess — and it always is — having the raw count
beside the derived rpm is what settles an argument.

The count is **pulses per second, not rpm**: revolutions per pulse is the fan's
property and not the board's, so the conversion (`rpm = pulses * 60 / pulses
per revolution`, usually 2) belongs to whoever knows which fan is fitted. A
whole-second window needs no reciprocal and no division, and 1 pulse/s — 30 rpm
on a 2-pulse fan — is finer than a fan's own speed regulation. The counter
saturates instead of wrapping: a wrapped count reads like a slow fan, which is
the one wrong answer that looks plausible.

<a id="measured-on-the-hardware"></a>
<a id="24-measured-on-the-hardware"></a>
### 2.4 Hardware validation

`board/` loaded, writing `pwm1` under hwmon and reading `FAN_STATUS`:

| `pwm1` | tach pulses/s | `[18]` fallback |
|---|---|---|
| 255 | 142 | 0 |
| 200 | 121 | 0 |
| 150 | 97 | 0 |
| 100 | 72 | 0 |
| 60 | 45 | 0 |
| 30 | 19 | 0 |
| 0 | 141, back at full speed | **1** |
| any, with `FAN_CTRL[1]` set | **0** | 0, `[19]` set |

Monotonic across the range, and the last two rows are the two ways the fan
stops being the PWM's to decide: at 0% the fabric takes it back to full speed
on its own, and `FAN_CTRL[1]` is what actually stops it.

`pwm1 = 255` leaves the fallback clear, so `pwm-cadence` is not producing a
perfectly static high at full scale — there are still edges. It lands on full
speed either way.

<a id="-pwm1--0-is-not-how-you-stop-the-fan"></a>
<a id="25--pwm1--0-is-not-how-you-stop-the-fan"></a>
### 2.5 Force-off control

The TTC waveform's **resting level at 0% duty is not defined**. Measured on this
board, the same `pwm1 = 0` went both ways:

| How 0% was reached | Waveform rested |
|---|---|
| Ramped down 255 → 200 → ... → 30 → 0 | LOW |
| Stepped down 255 → 0 | HIGH |

Through an inverter those are opposite fan states, and nothing on the wire can
tell a waveform resting high from a legitimate 100% duty. What saves it is
that neither resting level has **edges**: the fallback fires either way, so
`pwm1 = 0` lands on full speed whichever way the waveform stopped. That is
deterministic, and it is the safe direction.

It also means `FAN_CTRL[0]` alone is not a way to stop the fan. Clearing the
fallback at `pwm1 = 0` hands the pin back to that undefined resting level, and
the fan then runs or stops depending on how 0% was arrived at. Stopping the
fan is an explicit request: `FAN_CTRL[1]`.

## 3. Frequency counters

Four oscillators on this board have no other consumer in the fabric, so
nothing else would reveal a fault in them: a part that was not fitted, or is
dead, or was fitted at the wrong frequency looks exactly like one nothing
happens to use.
`freq_ctr.v` counts each against the PS clock over a one-second gate, so the
reading **is** the frequency in Hz, and Linux reads it out of a register.

**Measured on the hardware:**

| Register | Oscillator | Reading | Nominal | Error |
|---|---|---|---|---|
| `FREQ0` | Y2, 50 MHz, `PL_CLK` (AD18) | **50,000,207 Hz** | 50 MHz | +4.1 ppm |
| `FREQ1` | Y8, 156.25 MHz GTX ref, through SFP1's user clock | **78,125,420 Hz** at the reset rate, Y8 ÷ 2 | 78.125 MHz | +5.4 ppm |
| `FREQ2` | Y9, 150 MHz SATA ref ÷2 | **75,000,753 Hz** | 75 MHz | +10.0 ppm |
| `FREQ3` | Y7, 200 MHz `SYS_CLK` | **200,001,364 Hz** | 200 MHz | +6.8 ppm |

All four present and correct, read at one moment. `FREQ_UPDATES` read
`0xE0E0E0E0` -- 224 completed measurements on every channel, so none of these
is a stuck zero.

⚠ **The two GTX references reach their counters by different routes.** An
`MGTREFCLK` pin feeds the transceiver quad, not the fabric. Y9, the SATA
reference, is counted through `IBUFDS_GTE2`'s `ODIV2`, which divides by two,
so that reading is HALF the oscillator. In `ddr/`, which has no transceivers,
Y8 is counted the same way. In `board/`, Y8's buffer has only one route into
the fabric and the SFP transceivers need it (see "The SFP+ cages"), so Y8 is
counted through SFP1's user clock, its `TXOUTCLK`: the line rate / 40,
phase-locked to Y8 by the PLL SFP1's `RATE` selects, so it carries Y8's ppm
unchanged -- 78.125 MHz at the reset rate, 156.25 at 6.25 Gb/s and 257.8
through the QPLL at 10.3125. It reads zero while the transceivers are held in
reset. That both answer at all confirms MGTAVCC,
MGTAVTT and MGTVCCAUX are up.

⚠ **This measures a ratio to the PS oscillator**, scaled by an assumed 100 MHz.
An error in PS_CLK moves every reading together — which is what the four
same-signed offsets above look like, rather than four independently fast
crystals. It answers "is it there and is it the right frequency", not "how
accurate is it".

A clock that never runs leaves its initial reading at zero. A clock that
stops later retains its last reading. Poll the 8-bit wrapping update count
over a measurement interval to detect progress; a single zero is ambiguous.

## 4. BIST engines

A CPU access through `M_AXI_GP0` is 32 bits wide, one `devmem` at a time.
That proves a path exists, but it does not exercise `S_AXI_HP`, it never
interrupts the CPU, and it cannot measure bandwidth, because the CPU issuing
the accesses would be the bottleneck being measured.

`axi_bist.v` is an AXI master that fills memory with a pattern, reads it back,
checks it, and reports errors, elapsed cycles and beats. Each instance gets a
64-byte register window (see "Registers" under `board/` below).

**Measured on the hardware** with `pl/tools/bisttest.sh -m 8`:

| | |
|---|---|
| `S_AXI_HP1` | 16,777,216 bytes in 2,100,168 cycles → **798 MB/s**, 0 errors |
| `S_AXI_HP2` | 16,777,216 bytes in 2,100,261 cycles → **798 MB/s**, 0 errors |

798 of a theoretical 800 MB/s — 64 bits at 100 MHz, 99.8% of the port. Each
engine can also interrupt the CPU when a run completes.

`CTRL.STOP` prevents new bursts and drains address offers already presented
to the slave, including an offer stalled before acceptance. A watchdog is an
emergency abort: if transactions were in flight, reset the affected AXI path
before reuse. The no-response simulation case exercises an unaccepted offer;
it does not qualify recovery from partially accepted hardware transactions.

The test proves rather more than "no errors", which a self-contained
write-then-read cannot:

- the CPU reads back varying data at the target, so the writes really landed
  in PS DRAM rather than somewhere the engine was talking to itself
- **a word the CPU changes is detected** by the next read+check pass, which
  is what proves the engine and the CPU are addressing the same memory
- **HP2 verifies what HP1 wrote**, so the two ports agree
- both engines wake a blocked reader on `/dev/uio0` and `/dev/uio1`

⚠ **The pattern is a function of the address.** A pattern from an LFSR would
be written and read back in the same order, so an engine that put every burst
at one wrong place would still pass. Each 32-bit lane is derived from its own
byte address, so data that lands anywhere other than where it was aimed reads
back as a mismatch.

⚠ **No bounds check.** An engine writes wherever `ADDR` points, at 64 bits a
clock. The device tree reserves the top 16 MB of PS DRAM for them; see
"The BIST engines" in [the Linux guide](linux-guide.md).

<a id="engine-2-pl-ddr3-from-inside-the-fabric"></a>
<a id="41-engine-2-pl-ddr3-from-inside-the-fabric"></a>
### 4.1 PL DDR3 engine

Both designs fit a third engine on the MIG -- at `0x140` in `board/`, at
`0xC0` in `ddr/` -- so the PL's own gigabyte can be swept by the fabric instead
of one `devmem` at a time.

It shares the MIG's single AXI port with the CPU through `axi_owner.v`, one
owner at a time. `AUX[0]` (register `0x3C`) asks for the handover; `AUX[16]`
says who actually has it. The switch is **deferred until offered addresses, accepted bursts and responses drain**,
because switching mid-burst would leave the MIG waiting for write beats from
a master that no longer owns the data channel.

⚠ **Whoever does not own the bus is answered SLVERR**, not left waiting. A
master hung on the PL bus on this board means a JTAG `rst -system`; a bus
error is something the kernel reports and survives. So while the engine owns
the MIG, a CPU access to PL DDR3 raises a bus error — that is the design
working, not failing. The error responder returns exactly the beats a read
asked for, up to AXI4's 256.

⚠ **Engine 2's addresses are OFFSETS INTO THE DRAM, starting at 0.** It talks
to the MIG directly. The CPU reaches the same memory at `0x4000_0000` because
that is where `M_AXI_GP0`'s window sits and the MIG only sees the low 30 bits.
Aiming the engine at `0x4000_0000` happens to work — it wraps to offset 0 —
which is the right answer for the wrong reason.

`AUX[27:18]` report why a handover is still pending: `[18]` idle, `[19]`
`w_busy` (an unmatched write address/data burst or a partial data burst),
`[23:20]` outstanding AW and `[27:24]` outstanding AR. The
outstanding counters clamp at zero (`axi_owner.v`), so an unexpected B or R
response cannot wrap one to 255 and hold `idle` false forever. With the counts
visible, a stuck handover is diagnosed with one read.

<a id="getting-past-800-mbs"></a>
<a id="42-getting-past-800-mbs"></a>
### 4.2 Throughput limit

That figure is the port, not the memory. All four HP ports are in use in
`board/`: HP1 and HP2 by the BIST engines, HP0 and HP3 by the two VDMAs. More
BIST bandwidth means running both engines at once, or clocking them from
`FCLK1` (200 MHz, generated and unused). The engines run on `fclk_clk0` at
100 MHz because one clock domain is easier to trust than two.

<a id="hdmi-output"></a>
## 5. HDMI output

`hdmi_out.v` makes a pixel clock, generates CEA timing and drives 24-bit RGB
into the ADV7511. The chip does TMDS, DDC and CEC in silicon; Linux configures
it over the bit-banged I2C bus with [`tools/hdmitest.sh`](../pl/tools/hdmitest.sh).

The output is a **test pattern, not a framebuffer**, on purpose.
Driving a monitor from PS DRAM needs a pixel clock, CEA timing, the I2C setup,
the parallel bus, an AXI master, a cross-clock FIFO and a scanline prefetcher —
and if the screen stays black, all seven are suspects. A pattern generator
removes the last three, so anything appearing at all has already settled the
other four.

| Mode | Resolution | Nominal clock |
|---|---|---|
| 0 (default) | 1280×720p60 | 74.25 MHz |
| 1 | 1920×1080p60 | 148.5 MHz |
| 2 | 640×480p60 | 25.175 MHz |

**The HD pixel clocks are exact.** The MMCM divides the 200 MHz oscillator by
8 and multiplies by 37.125 (a 928.125 MHz VCO), then divides by 12.5 for
**74.25 MHz** or 6.25 for 148.5 MHz: 60.000 Hz frames. 640×480's 25.175 MHz
has no exact setting; 200 × 4.5 ÷ 35.75 = 25.1748 MHz is 7 ppm low. The
settings follow from `MODE`, so the clock cannot disagree with the timing,
and `sim/hdmi_out_tb.v` computes each mode's frequency from the MMCM
parameters the instance actually carries.

⚠ The pattern's **moving bar is not decoration**. A still image cannot be told
apart from a frozen one: a monitor showing perfect color bars proves the
ADV7511 latched a frame, not that the fabric is still producing them. If the
bar stops, the pixel clock or the timing generator has stopped. The one-pixel
border is the only thing that shows whether the active area is where the sink
thinks it is.

⚠ **Audio is impossible on this board.** The ADV7511's I2S and SPDIF inputs are
strapped on the PCB rather than routed to the PL (schematic sheet 18). No
configuration carries samples to it — that is a wire that does not exist.

<a id="measured-with-an-hdmi-cable-from-hdmi1-back-to-hdmi2"></a>
<a id="51-measured-with-an-hdmi-cable-from-hdmi1-back-to-hdmi2"></a>
### 5.1 Loopback validation

The loopback gives the transmitter a real sink, so the `-f` HPD override is
not needed:

| | |
|---|---|
| `0x42` = `0xd0` | **HPD asserted** -- the ADV7611 is pulling hot-plug high |
| `0x41` = `0x10` | the chip stays powered up on its own, with no override |
| `0x9E` = `0x12` | its PLL is locked to our pixel clock |
| ADV7611 `0x6F` bit 0 | **set** -- the receiver detects a TMDS clock on its input |

So the transmitter drives a real signal, the cable carries it, and the
receiver at the far end sees the clock arrive.

<a id="-load-an-edid-into-the-receiver-or-hpd-drops"></a>
<a id="52--load-an-edid-into-the-receiver-or-hpd-drops"></a>
### 5.2 EDID and hot-plug detection

`0x42` on the ADV7511 reports hot-plug and monitor sense, and over the
loopback it moves with what the *receiver* is doing:

| ADV7511 `0x42` | When |
|---|---|
| `0xd0` | HPD asserted, monitor sense low -- receiver unconfigured, power-on defaults |
| `0xb0` | HPD **low** -- the `adv7604` driver has taken over and set automatic HPD control, which requires an active internal EDID, and there is none |
| `0xf0` | HPD **and** monitor sense asserted -- an EDID has been loaded |

So the driver binding makes HPD *worse* until an EDID is loaded:

```
v4l2-ctl -d /dev/v4l-subdev0 --set-edid=type=hdmi
```

That is worth doing on principle: it gives the receiver a physical address, it
is what a real sink presents, and it is the state a transmitter expects.

Once the `adv7604` driver has configured the receiver it goes further:
ADV7611 `0x6A` reads **`0x53`** -- TMDS signal detected *and locked* -- and
the capture path recovers 1280x720p60 from it. See "HDMI input" below.

⚠ Read before the driver binds, `0x6A` is `0x00` however good the signal is:
an unconfigured ADV7611 keeps its core powered down. A reading taken then says
nothing about the cable.

<a id="measured-with-no-cable-attached"></a>
<a id="53-measured-with-no-cable-attached"></a>
### 5.3 Disconnected-output checks

Everything up to the connector is proven:

| | |
|---|---|
| `STATUS[1]` | **1** — the MMCM locked and is producing the pixel clock (synchronized into the register clock) |
| ADV7511 at 0x39 | answers, revision `0x14`, takes the setup |
| `0x9E` bit 4 | **set** — the ADV7511's PLL is locked to our pixel clock |

So the MMCM's pixel clock leaves through the ODDR, reaches the chip on the right
pin, and the chip locks to it. What has **not** been shown is a picture, which
needs a monitor.

⚠ **The ADV7511 powers itself down when HPD is low**, whatever is written to
`0x41`. With no cable, `0x41` is written as `0x10` and reads back `0x50` — bit
6, power-down, set by the chip itself — and `0x9E` then reads `0x00` because an
unpowered PLL cannot lock to anything. That is not a fault, but it makes the
two most useful diagnostics read exactly as they would if the pixel clock were
dead. `hdmitest.sh -f` sets `0xD6[7:6] = 11` so the chip behaves as though HPD
were asserted; that is how the lock above was measured.

<a id="hdmi-input"></a>
## 6. HDMI input

`hdmi_rx_capture.v` turns the ADV7611's parallel video into AXI4-Stream video
for a Xilinx AXI VDMA, so that Linux sees an ordinary V4L2 capture device:

```
HDMI2 -> ADV7611 -> 24-bit RGB + LLC/DE/HS/VS -> hdmi_rx_capture -> AXI VDMA -> S_AXI_HP0 -> PS DRAM
            |                                                          |
      adv7604 over i2c-gpio                                  xilinx_dma, xilinx-vipp -> /dev/video0
```

Every driver in that path is mainline and already built into this kernel:
`adv7604` for the receiver, `xilinx_dma` for the VDMA, and `xilinx-vipp` plus
`xilinx-dma` for the V4L2 device. Nothing here needs a driver written.

<a id="measured-on-the-hardware-with-hdmi1-looped-back-to-hdmi2"></a>
<a id="61-measured-on-the-hardware-with-hdmi1-looped-back-to-hdmi2"></a>
### 6.1 Loopback timing

The fabric captures the board's own HDMI output, through TMDS and back:

| | |
|---|---|
| `h_active` x `v_active` | **1280 x 720** |
| `h_total` x `v_total` | **1650 x 750** -- exactly CEA-861 720p60 |
| frame rate | 11016 to 11139 frames in ~2 s = **60 fps** |
| `stalls` | **0**, and the sticky abandon flag is clear |
| ADV7611 `0x6A` | `0x53` -- TMDS signal detected **and locked** |

Those totals are not something this design produced: they are what the
ADV7611 recovered from the TMDS stream and clocked out on its own LLC, and
they match the standard exactly. Read twice a few seconds apart, the numbers
are identical.

⚠ Read immediately after the receiver is configured they are 1282 x 719 --
the ADV7611 is still settling. Anything measured in the first moments after
configuration is a transient, not a result.

<a id="-devvideo0-captures-the-loopback"></a>
<a id="62--devvideo0-captures-the-loopback"></a>
### 6.2 V4L2 capture

Booting `zynq-rkz7100-hdmirx.dtb`:

```
xilinx-vdma 80000000.dma: Xilinx AXI VDMA Engine Driver Probed!!
xilinx-video video-capture: device registered
adv7611 1-004c: adv7611 found @ 0x98 (i2c-hdmi-rx)
```

`v4l2-ctl -d /dev/v4l-subdev0 --query-dv-timings` reports **1280x720p60
(1650x750), 74,250,000 Hz, CTA-861 VIC 4**. Ten frames captured to a file
are **27,648,000 bytes = 10 x 1280 x 720 x 3**, exactly.

⚠ **Give the receiver an EDID first.** Until something does, the ADV7611
holds hot-plug low, and the ADV7511 powers itself down while HPD is low -- so
the transmitter's PLL never locks and there is nothing to capture:

```
v4l2-ctl -d /dev/v4l-subdev0 --set-edid=type=hdmi
```

⚠ Two more settings have to be made before streaming, and `tools/hdmirxtest.sh
-c` makes both. The receiver's source pad comes up as `YUYV8_2X8`, so it is
set to `RGB888_1X24` at the detected size with `media-ctl`, and the capture
node to `BGR3` at that size; until then `ENUM_FMT` offers nothing and
`REQBUFS` fails. And if the cable went into HDMI2 after boot, the ADV7611's
termination has been reset to off -- see known issue 14 in the
[user guide](RK_ZYNQ7100_User_Guide.md).

The content is checked against what `video_tpg.v` is designed to draw, not
against a second copy of the capture. Sampling row 100 across the width:

| x | captured B G R | the bar the generator puts there |
|---|---|---|
| 80 | `01 01 01` | black |
| 240 | `f3 01 01` | blue |
| 400 | `01 fe 01` | green |
| 560 | `fe fe 0b` | cyan |
| 720 | `01 01 fb` | red |
| 880 | `fe 01 fe` | magenta |
| 1040 | `13 fe fe` | yellow |
| 1200 | `fe fe fe` | white |

The byte order in memory is B, G, R, as `V4L2_PIX_FMT_BGR24` requires.

Every edge is on its pixel: x=0 is the white border and x=1 black, x=159 is
still black and x=160 is the first blue pixel, x=320 the first green, x=1120
the first white, and x=1279 the border again; rows 0 and 719 are white. That
needs `hdmi_out.v` to register DE, HSYNC and VSYNC alongside the registered
pattern; without it every pixel would leave one clock after its DE and each
bar would start one pixel late. `sim/hdmi_out_tb.v` checks the same alignment.

Two further checks, because a still picture cannot be told from a frozen one:

| | |
|---|---|
| a static color-bar row, frame 0 vs frame 1 | **byte-identical** -- no sampling noise |
| the moving-bar row, frame 0 vs frame 1 | **differs** -- the pipeline is live |
| re-read forty minutes later | still 1280x720, still 60 fps, still 0 stalls |

The last row matters: a capture path that ran for a few seconds after
configuration and then drifted would look identical in a single measurement.

⚠ The saturated colors come back slightly short: blue reads `f3` where `ff`
was sent, and the cyan and yellow bars are off by a little on one channel.
That is **not** the fabric. A sampling error could not be stable, and these
values are identical at both ends of the same bar and across captures -- the
ADV7611 is emitting them. Blue, cyan and yellow are the three colors a
YCbCr round trip clips hardest, which is what the pair of ADV chips does
internally. The `rx_rgb_quantization_range` control does not change it.

<a id="-720p60-and-below----1080p60-does-not-close"></a>
<a id="63--720p60-and-below----1080p60-does-not-close"></a>
### 6.3 Supported capture timings

The pixel clock is constrained at **74.25 MHz**, which covers 720p60,
1080p30, 576p, 480p and VGA. 1080p60's LLC is 148.5 MHz and this build does
not meet timing there.

The reason is worth knowing, because it is not the logic. The LLC reaches the
capture flops through an IBUF and a BUFG: 4.43 ns of clock insertion delay
against about 1.6 ns for the data, which is a hold violation. The placer
fixes hold the only way it can, by inserting a **ZHOLD delay element in the
data path** -- it chose 7.106 ns. Hold is then satisfied and there is nothing
left for setup, so 148.5 MHz misses by 1.4 ns with the entire violation being
one automatically inserted delay. At 74.25 MHz the same 7.1 ns fits inside
the period and the design closes untouched.

Closing 1080p60 needs the clock to arrive on time rather than the data to be
delayed: an MMCM whose feedback compensates the BUFG insertion delay, so the
clock at the flops is phase-aligned with the clock at the pin. That MMCM must
re-lock whenever the source changes resolution, with the capture block and
the CDC FIFO's write side on its output; 720p60 and below do not need it.

<a id="-the-frame-boundary-comes-from-de-not-from-vsync"></a>
<a id="64--the-frame-boundary-comes-from-de-not-from-vsync"></a>
### 6.4 Frame boundary detection

Keying the frame off VSYNC means knowing VSYNC's polarity, which changes with
the video mode and which the `adv7604` driver programs without telling the
fabric. Getting it wrong does not fail loudly: frames come out offset by a
vertical blanking interval, which looks like a picture rolled a few lines, and
the natural suspect is the monitor or the source.

DE has no polarity. DE high means "this clock carries an active pixel", in
every mode and every chip. Lines are the runs of DE, and the frame boundary is
the one gap between runs that is much longer than a line -- the threshold is
two measured line periods, so it adapts to whatever the source sends. Every
CEA-861 mode has at least five lines of vertical blanking, so no mode puts two
line periods on the wrong side of that gap.

⚠ A line period is only believed once **two consecutive measurements agree**.
A single one can be the interval from reset to the first DE, which is an
arbitrary number -- on hardware, whenever the bitstream happened to load -- and
believing it can drop the threshold below a horizontal blanking interval, at
which point every line looks like a frame. Until two agree, the threshold is
a fixed 16,383 clocks: above the longest CEA-861 horizontal blank (2,680, at
720p25) and below the shortest vertical one (36,000, at 480p), so even the
first frame after the bitstream loads is found in every mode.

HSYNC and VSYNC are still watched. Their activity and observed polarities land
in a status register, and they make good diagnostics precisely because nothing
depends on them.

<a id="-a-capture-source-cannot-be-stalled"></a>
<a id="65--a-capture-source-cannot-be-stalled"></a>
### 6.5 Backpressure

The ADV7611 sends pixels whether or not the VDMA is ready. One low cycle on
TREADY destroys a pixel, and there is nowhere to put it.

Dropping it and carrying on would corrupt the frame geometry permanently,
because the VDMA counts beats: the picture would shear and never recover. So a
stall **abandons the rest of the frame**. The stream goes quiet until the next
start of frame, the VDMA resynchronizes on that TUSER, and the cost is one
dropped frame. The stalls are counted in a register, so the cost is visible
rather than inferred.

<a id="status-registers"></a>
### 6.6 Status registers

Published to the PS clock once a frame, through a toggle handshake:

| | |
|---|---|
| `STAT0` | `{h_total, h_active}` |
| `STAT1` | `{v_total, v_active}` |
| `STAT2` | `{stalls, frames}` |
| `STAT3` | `{updates, flags}` -- DE/HS/VS seen, the two observed polarities, streaming, and the sticky abandon flag |

⚠ `updates` is what separates a dead pixel clock from a black picture. With no
LLC nothing in that domain ever fires, so every register keeps its reset value
**and** `updates` stays at zero. Zeroes on their own would be ambiguous.

<a id="the-bench"></a>
<a id="67-the-bench"></a>
### 6.7 Simulation

`pl/sim/hdmi_rx_capture_tb.v` runs 720p, 1080p and 640x480 concurrently. Its
stimulus is `video_timing.v` -- the generator that drives the HDMI *output*,
itself checked against CEA-861 constants written out a second time -- so the
capture block is not being fed its own assumptions.

Every pixel carries its own coordinates, `d = {y, x}`, so a dropped pixel, a
duplicated one, a repeated line or a frame that starts one line late is caught
at the first wrong beat and named. A check that counted beats per line passes
on all four.

640x480 is in the set because its syncs are **negative** where the other two
are positive, and the pixel and register clocks are deliberately
incommensurate, so the snapshot handshake crosses a real asynchronous boundary.

The backpressure case is the one that matters: one low cycle on TREADY must
abandon exactly that frame, leave the next one perfect to the last pixel, and
show up in `STAT2`. A block that ignored the stall entirely fails it in all
three modes.

<a id="the-capture-patch"></a>
<a id="68-the-capture-patch"></a>
### 6.8 Driver integration

`linux/board/patches/linux/0001-xilinx-vip-accept-the-ADV7611-RGB888-media-bus-code.patch`.

The `adv7604` driver reports `MEDIA_BUS_FMT_RGB888_1X24` on its source pad.
The Xilinx VIP format table knows only `MEDIA_BUS_FMT_RBG888_1X24`, so without
the patch `VIDIOC_ENUM_FMT`, `VIDIOC_G_FMT` and `VIDIOC_STREAMON` all return
`-EINVAL`. The new entry has to come *before* the existing RBG888 one, because
`xvip_dma_verify_format()` compares the code found by fourcc against the code
the subdev reports and both lookups return their first match.

The byte order is not a coincidence. With `OP_CH_SEL = RGB` the ADV7611 drives
P23-P16 = R, P15-P8 = G, P7-P0 = B; the capture block passes that straight
through; the VDMA writes `TDATA[7:0]` to the first byte in memory. Memory
therefore reads B, G, R -- which is what `V4L2_PIX_FMT_BGR24` means.

<a id="-cec-over-the-hdmi1--hdmi2-loopback"></a>
<a id="69--cec-over-the-hdmi1--hdmi2-loopback"></a>
### 6.9 CEC loopback

Working, in both directions, through the Linux CEC stack. `pl/tools/cectest.sh`
runs the whole thing and says which case it saw.

It needs a kernel patch, because **this board does not connect the ADV7611's
interrupt**: `INT1` (pin 55) is a bare stub on schematic sheet 19, and so are
the alternate `SCLK/INT2` (49) and `MCLK/INT2` (51); pin 1 is wired but used
for its `HPA` function. There is nothing to declare in the device tree, so
`client->irq` is 0.

For video that is survivable, since userspace re-reads the timings. For CEC it
is fatal, because in `adv7604.c` `cec_transmit_done()` is reached **only** from
`adv76xx_cec_isr()`, inside `adv76xx_isr()`, and the IRQ is requested only
`if (client->irq)`. On a kernel without the patch, every CEC frame is
transmitted and acknowledged on the wire while the CEC core is never told, and
each transmit times out:

    cec-1-004c: message 00 timed out

`linux/board/patches/linux/0002-adv7604-poll-the-status-registers-when-no-interrupt-is-wired.patch`
adds a `delayed_work` that calls `adv76xx_isr()` when there is no interrupt.
The chip's status bits latch whether or not they are unmasked onto the pin, so
polling does exactly what the interrupt would have caused. A quiet poll is
three register reads plus one for CEC, and the CEC ISR returns immediately when
its status byte is zero. The interval is the `adv7604.poll_interval` module
parameter, default 20 ms. The boot log says so:

    adv7611 1-004c: no interrupt wired, polling status every 20 ms

**Measured with the patch in place:**

| | |
|---|---|
| Logical address | allocates — `Logical Address: 0 (TV)`, mask `0x0001` |
| Poll to the transmitter | `cec-ctl --to 4 --poll` is **acknowledged** |
| Poll to an empty address | `cec-ctl --to 8 --poll` gives `Tx, Not Acknowledged (2), Max Retries` |

That last row is the point: the test can distinguish, so the row above it means
something.

**What the polling costs, measured on the board** (the interval is writable at
`/sys/module/adv7604/parameters/poll_interval`, so both cases are one boot):

| | |
|---|---|
| One register read | **~0.4 ms** — 300 reads take 2.40 s against 2.26 s for 300 bare process spawns, which matches `i2c-gpio,delay-us = <5>`, about 100 kHz |
| One poll | 4 reads, so **~1.6 ms**, i.e. roughly **8% duty on the HDMI-RX I2C bus** at 20 ms |
| CPU | **not measurable**: 4 busy ticks per 30 s against 2 with polling off, on two CPUs — the bit-bang delay does not burn CPU that `/proc/stat` attributes |
| Contention | **not measurable**: 300 reads take 2.355 s with polling on and 2.360 s with it off |

So the cost is 8% of a bus that carries nothing else — the ADV7611 is the only
device on `i2c-hdmi-rx`, and the video driver touches it only on ioctls. 20 ms
is chosen for CEC *receive*: the chip buffers one message, and CEC frames are
at least ~24 ms apart, so a slower poll risks dropping back-to-back messages.
Transmit completion would tolerate far more. A larger interval makes polling
proportionally cheaper; nothing turns it off.

⚠ **Only the receiver is a Linux CEC device.** The ADV7511 has no driver
here — its CEC lives in a DRM bridge driver that needs a DRM pipeline, and this
board has none — so the transmit side is configured over I2C by hand, which
`cectest.sh` does. That configuration is volatile and is lost on every power
cycle.

⚠ **There is only one pull-up on this bus.** R179, 27K to +3.3V through the
Schottky D5, sits on the **transmit** connector; the ADV7611 end has none of
its own. The receiver can therefore only transmit when the cable carries pin 13
through; a cable that omits it leaves the receiver unable to transmit at all,
while the transmitter still can.

**Reading the transmitter's CEC status by hand.** The ADV7511 has no driver
here, so anything it reports has to be decoded manually. The bits are defined
in `adv7511-v4l2.c`, and are easy to read backwards:

| Main map `0x97` (INT1) | meaning |
|---|---|
| `0x20` | **transmission succeeded** |
| `0x08` | retry failed — NACK count in CEC `0x14` low nibble, low-drive count in its high nibble |
| `0x10` | arbitration lost |

The receiver's equivalent is IO `0x93`, cleared by writing to `0x94`, where
`0x01` is success, `0x04` retry failed, `0x02` arbitration lost and `0x08` a
received message.

⚠ A **broadcast** frame reports success whether or not anything is
listening, so prove a link with a *directed* message to an address that is
enabled at the far end.

⚠ A timeout is not a NACK. During logical address allocation a NACK means
the address is free, and *succeeds*; a timeout means the frame never completed
as far as software knows, which points at the notification path rather than the
wire.

<a id="7-the-camera"></a>
## 7. Camera

J9's two MIPI lanes into a CSI-2 receiver, and from there into PS DRAM:

```
J9 --2 lanes--> mipi_csi2_rx_subsystem --> cam_guard --> axi_vdma --> S_AXI_HP3
                (soft D-PHY, bank 35)        (FIFO)      (16-bit stream)
                   0x8002_0000                              0x8001_0000
```

**Measured:** 640x480, 1296x972, 1920x1080 and 2592x1944 -- 315 to 472.5 Mb/s
per lane -- all deliver whole frames with the sensor's color bars exact and
the receiver's ECC, CRC and start-of-transmission counts at zero, at 67.5,
32.1, 33.0 and 16.8 frames a second; streams restart back to back.
[`tools/camtest.sh`](../pl/tools/camtest.sh) on the board runs it all.

| | |
|---|---|
| The receiver | `csi_cam`: 2 lanes, RAW10, one pixel a beat, the video frame buffer in; line rate 480 Mb/s, above the fastest mode; the D-PHY's register interface on (registers at `+0x1000`) |
| The pins | HS on `LVDS` with `DIFF_TERM FALSE` -- the board fits 150R across each pair -- and LP on `HSUL_12`, bank 35 `INTERNAL_VREF 0.6` |
| Clocks | `lite_aclk` and `video_aclk` on FCLK_CLK0, `dphy_clk_200M` from the Y7 oscillator; the byte clock is recovered from the sensor's clock lane, its own asynchronous group |
| The VDMA | `vdma_cam`, the HDMI one's twin with a 16-bit stream and a 4096-deep line buffer, entirely on FCLK_CLK0 |
| Reset | the receiver's `video_aresetn` is also EMIO gpio 110, synchronized: the driver's `video-reset-gpios` |

⚠ **`cam_guard` is what keeps a stream alive.** Every stream begins with a
partial frame that has no frame start. Fed straight into the VDMA, about 300
lines of it go in and the VDMA stops taking data; the receiver's frame buffer
then fills, and `xilinx-csi2rxss` answers "stream line buffer full" by
disabling the core until the stream is stopped, so only the first stream after
boot works. The guard always accepts from the receiver,
buffers 2048 beats, and on overflow or an idle gap of 200 us drops to the next
frame start. Its drop counter shows the partial frame on every stream: about
1.26 million beats -- one frame -- on the first after boot, about 0.76 million
on later ones. `AUX[15]` = 1 turns the dropping off, for comparison.

⚠ **The input delay is the D-PHY's register, not the IP's tap ports.** With
the register interface on, the data lanes' IDELAYs take their tap from
`+0x04` (a byte per lane, 78 ps a tap); the `lane0_tap`/`lane1_tap` ports
are unused and tied off. Swept against the receiver's damaged-packet counts,
the clean window depends on the line rate:

| Mode | Per lane | Clean taps |
|---|---|---|
| 640x480 | 315 Mb/s | 0..25 and 31, apart from single damaged packets from a stream start |
| 1296x972, 1920x1080 | 441 Mb/s | 1..19 |
| 2592x1944 | 472.5 Mb/s | **30 and 31 only** -- thousands of damaged packets in ten frames anywhere below |

No one tap serves all four, so the register resets to 10 (`C_IDLY_TAP`, in
`build.tcl`), clean for the lower three, and
[`tools/camsetup.sh`](../pl/tools/camsetup.sh) sets 31 for 5 MP.
`camtest.sh -t WxH [lane [hold]]` repeats the sweep.

⚠ **The window depends on placement.** The edges of the 441 Mb/s window move
between bitstreams (tap 31 is clean in one build and damages a dozen packets
per 30 frames in another), while the 5 MP window stays at 30 and 31.
Re-sweep after a rebuild that moves bank 35's logic.

⚠ **A color-bar comparison alone cannot see a dropped line.** The bars are
identical in every frame and the capture buffers are reused, so a line the
receiver discards for a bad CRC leaves the previous frame's identical line in
place. A sweep on color bars alone passes every tap for that reason, so
`camtest.sh` also reads the receiver's counts.

⚠ The HS-settle time (`+0x30`, `+0x48`, in ns) is not the lever: 100 to 155
makes little difference to the damaged-packet count at a bad tap, and 170 and
above breaks start-of-transmission detection outright.

The bench, `sim/cam_guard_tb.v`, pins the guard: clean frames pass whole, a
stream that starts mid-frame is cut to whole frames, a stall longer than the
FIFO costs exactly the frame it cuts while the receiver is never held off,
and with the guard off the same stall holds the receiver instead.

<a id="8-the-sfp-cages"></a>
## 8. SFP+ cages

Only **two low-speed signals per cage** reach the FPGA: `TX_DISABLE` out
and `LOS` back. The high-speed TX/RX pairs connect separately to the GTXs.
MOD-DEF0/1/2 -- the module I2C and the presence detect -- RS0 and RS1 all end
at a 4.7K pull-up and go nowhere, and TX_FAULT is tied to ground. A module
cannot be identified, detected or rate-selected from this board, only enabled
and watched.

Both are handed to Linux as EMIO GPIOs, named in the device tree:

| Line | gpiochip0 | |
|---|---|---|
| `SFP1-TX_DISABLE` | 106 | out, **active high**, pulled up |
| `SFP2-TX_DISABLE` | 107 | out, **active high**, pulled up |
| `SFP1-LOS` | 108 | in |
| `SFP2-LOS` | 109 | in |

⚠ **A module's transmitter is OFF until software drives `TX_DISABLE` low.**
The 4.7K pull-up is the power-on state, and `emio_pads` releases a line rather
than driving it high, so that is also where it returns if software stops. An
SFP fitted to this board and "not linking" has usually never been asked to
transmit.

```
gpioset --mode=signal gpiochip0 106=0 107=0 &   # both transmitters on
```

The `--mode=signal` and the `&` are not decoration: `gpioset` releases the
line when it exits, and the pull-up then switches the transmitter off again.

<a id="measured"></a>
<a id="81-measured"></a>
### 8.1 Hardware validation

| | |
|---|---|
| Copper SFP in each cage, `TX_DISABLE` released | **reads 1** on both -- the pull-ups are real and the pins are connected |
| Copper SFP, `LOS` | **reads 0** on both in every `TX_DISABLE` state -- a 1000BASE-T module reports nothing useful on it |
| Two legs of an active optical cable in SFP1 and SFP2, `TX_DISABLE` released | the legs are dark: the far end receives nothing, while the direction into this board stays error-free |
| The same, `TX_DISABLE` held low with the `gpioset` above | PRBS-31 error-free in both directions at 3.125, 6.25 and 10.3125 Gb/s |

So `TX_DISABLE` reaches the module and works. Copper modules cannot show
it -- they say nothing on `LOS` and the module I2C is not wired -- but an
optical module can. `pl/tools/sfptest.sh` drives both pins and reports what
`LOS` does.

<a id="-the-transceivers-3125-625-and-103125-gbs-through-a-passive-dac"></a>
<a id="82--the-transceivers-3125-625-and-103125-gbs-through-a-passive-dac"></a>
### 8.2 Transceiver validation

`gtx_prbs.v`, register block 3 at `0x100`, driven from Linux by
`pl/tools/gtxtest.sh` (`-r 0|1|2|all`). Each channel runs the transceiver's
own PRBS generator and checker at 3.125, 6.25 or 10.3125 Gb/s, chosen at run
time, and counts erroneous 40-bit words.

| | |
|---|---|
| SFP1 | GTX quad 112, channel 2 -- `GTXE2_CHANNEL_X0Y14`, TX P2, RX T6 |
| SFP2 | GTX quad 112, channel 3 -- `GTXE2_CHANNEL_X0Y15`, TX N4, RX P6 |
| Reference | `MGTREFCLK1_112`, R8/R7: Y8 at 156.25 MHz, into each channel's CPLL and the quad's QPLL |
| Line rate | per channel, from `RATE`: 3.125 Gb/s (CPLL, divider 2), 6.25 (CPLL, 1), 10.3125 (QPLL at 10.3125 GHz, 1); 40-bit raw data, no encoding |
| User clock | `TXOUTCLK` through a BUFG, the line rate / 40 -- 78.125, 156.25 or 257.8 MHz -- for both directions; constrained at 257.8 MHz whatever the rate |
| Loopback | run-time: `000` through the pins, `010` near-end PMA with no cable |
| Polarity | run-time, TX and RX separately, so a P/N swap is a register write |

**Measured, with a passive DAC cable between the cages, PRBS-31, 15 s a
stage, `gtxtest.sh -r all -t 15`:**

| Rate | Near-end PMA loopback | Through the cable | BER (95%) |
|---|---|---|---|
| 3.125 Gb/s | 0 errors in 4.7 × 10¹⁰ bits | 0 in 4.7 × 10¹⁰ | < 6.3 × 10⁻¹¹ |
| 6.25 Gb/s | 0 errors in 9.5 × 10¹⁰ bits | 0 in 9.5 × 10¹⁰ | < 3.2 × 10⁻¹¹ |
| 10.3125 Gb/s | 0 errors in 1.57 × 10¹¹ bits | 0 in 1.57 × 10¹¹ | < 1.9 × 10⁻¹¹ |

Each figure holds for both channels (the rule of three: 3/B). Every path
works at normal polarity, so there is no P/N swap on either one. `FREQ1`
follows the rate -- 78,125,420, 156,250,838 and 257,813,884 Hz, each +5.4 ppm
-- which shows the selected PLL locked to Y8.

⚠ **A rate change is more than the PLL and the divider.** Against the
wizard's own configurations of all three rates at 40 bits, two attributes
differ: `RXCDR_CFG` for every rate, and `PMA_RSV` above 6.6 Gb/s (0x00018480
below, 0x001E7080 above). Writing a channel's `RATE` runs a sequence in the
fabric: hold the channel in reset, write both attributes and the dividers
`TXOUT_DIV`/`RXOUT_DIV` over the DRP (read back on this board at 0x0A8-0x0AC
and 0x099-0x09A; the dividers at 0x088, keeping the other fields of 0x088 and
the other half of 0x0AC), switch `TX/RXSYSCLKSEL`, wait 100 us, and release
the wizard's startup FSMs.

⚠ **The divider is the attribute, not the `TXRATE`/`RXRATE` ports**, which
stay at 000. Those ports are sampled on the user clock, which here is
`TXOUTCLK` -- the clock the change stops and restarts -- and a change on them
starts the GTX's own rate-change reset on top of the startup FSMs' (UG476,
"TX Rate Change"). Using the attribute avoids that overlap.

⚠ **A receiver can fail to leave reset at a CPLL rate.** Intermittently, at
3.125 Gb/s, `gtxtest.sh` stops with `receivers did not come up` and `STAT`
reads `0x8B`: `cplllock`, `txresetdone` and `tx_fsm_reset_done` set,
`rxresetdone` and `rx_fsm_reset_done` clear. Seen after about 1.5 hours at
10.3125 Gb/s followed by a switch down, and twice in five PL loads as the
first access after a load; the same first access passed the other three
times. Writing RATE 2 and then RATE 0 brings the receivers back without a
reload, and `gtxtest.sh -r all` then passes every rate. The cause is not
established.

⚠ `PMA_RSV` is a PARAMETER default in the wizard's
channel wrapper, not a literal attribute, so a diff of the attributes misses
it -- and 10.3125 Gb/s then fails even in near-end loopback.

⚠ **The user clock is constrained at 10.3125 Gb/s whatever the wizard was
built for.** Vivado derives `TXOUTCLK`'s period from the attributes, which
describe 3.125 Gb/s, and would time the 257.8 MHz logic at 78 MHz. The XDC
creates `sfp1_TXOUTCLK`/`sfp2_TXOUTCLK` at 3.878 ns, and `build.tcl` checks
they exist with that period and that the QPLL sits in quad 112.

⚠ **A checker that is not checking reports zero errors.** So `gtxtest.sh`
injects one TX bit error in each direction and requires it to be counted at
the far end and nowhere else. An error sent from SFP1 is counted by SFP2's
checker only, and one from SFP2 by SFP1's only -- twelve injections in a row
each way. That is what proves the pattern crosses the cable, rather than
returning through a path inside the chip.

⚠ **One injected bit error is counted as a burst of 2 to 4 words, not one.**
The checker is self-synchronizing: it predicts each bit from bits already
received, so a bad bit is flagged again each time it is used as a tap, and
PRBS-31 (x³¹ + x²⁸ + 1) has two taps. The burst is constant for
as long as a link stays up, and changes with the word alignment the link
settles into after a reset, so one link can count 3 in one direction and 4
in the other. `gtxtest.sh` accepts 1 to 8.

⚠ **Y8's reference buffer has one route into the fabric, and the
transceivers take it.** Each gtwizard channel sequences its CPLL power-up (the
UG476 CPLL requirement) from the reference through a `BUFH`, which needs
`IBUFDS_GTE2.O` in the fabric; `O` and `ODIV2` cannot both have that route.
With a frequency counter on `ODIV2`, routing fails with two unroutable pins on
`O`; with that load removed, it routes completely. So `FREQ1` counts SFP1's
`TXOUTCLK` instead -- see "The oscillators".

⚠ **The two CPLL-sequencing `BUFH`s must sit in the transceivers' clock
region, `X1Y3`.** Left alone, the placer puts them in `X0Y3`, where
`IBUFDS_GTE2.O` cannot reach them. They are `LOC`ed to `BUFHCE_X1Y36`/`X1Y37`;
`CLOCK_REGION` is not an option, because Vivado accepts it only on a global
buffer and on a `BUFH` it is a critical warning and a no-op. `build.tcl`
checks after routing that both channels and both `BUFH`s landed where
intended.

⚠ **`drp_clock` sets the startup FSMs' timeouts.** The gtwizard hard-codes
`STABLE_CLOCK_PERIOD` from its DRP clock setting; at the default 60 MHz that is
16 ns, and on this design's 100 MHz clock every reset wait would run at 62%
of its intended length. `build.tcl` sets it to 100.

⚠ **Xilinx's IBERT cannot express a loopback between these two cages from
batch Tcl**, which is why this uses gtwizard and the transceiver's own PRBS.
`C_CHANNEL_QUAD_n` is a single channel select per quad, and
`C_PROTOCOL_GT_COUNT_1` counts lanes across quads, so two lanes in one quad is
refused and two quads give one channel each -- checked against every
encoding the IP accepts.

<a id="the-pl-ethernet-port"></a>
<a id="9-the-pl-ethernet-port"></a>
## 9. PL Ethernet

RJ2's PHY, an RTL8211F, is wired entirely to bank 11 -- RGMII and its MDIO. Its
MAC is the PS's **second** Ethernet controller, GEM1, brought out over EMIO as
GMII, and Xilinx's `gmii_to_rgmii` core in the fabric converts between the two.
Linux sees an ordinary `macb` interface, `eth1`: the MAC and the driver are the
PS's and the kernel's, not this repository's.

```
PS GEM1 --EMIO GMII--> gmii_to_rgmii --RGMII--> PHY2 --> RJ2
        --EMIO MDIO--> (register at MDIO 8) --MDC/MDIO--> PHY2 (at 1)
```

| | |
|---|---|
| PS7 | `ENET1` on EMIO with its MDIO, clock source External -- in `board/build.tcl`'s overrides only, so the `ddr` design and the boot's PS init are unchanged |
| The core | `gmii_rgmii_phy2`, shared logic **in** the core: its own MMCM makes the 125/25/2.5 MHz transmit clocks from the 200 MHz oscillator, and it owns the IDELAYCTRL for its receive path |
| Receive clock | `phy2_rxc` on AF20, an SRCC pin, `create_clock` at 8 ns, its own asynchronous clock group |
| RGMII delays | none in the PL: the core's timing assumes the PHY delays both clocks, which is the RTL8211F's strapped default |
| MDIO | GEM1's, through the core; the core's own register sits at address 8 |
| Status | `0xF4` in the register file -- see the register map |
| Timing | WNS +0.184 ns with the rest of the design |

**Measured,** with `eth0` down so that every packet crossed RJ2: DHCP and 20/20
pings at 1000, 100 and 10 Mb/s, the core's speed register following each
change; `iperf3` **666–674 Mbit/s** into the board and **562–807 Mbit/s** out
(the outbound figure swings run to run, on `eth0` too); and a 60-second
receive run of 4.8 GB with no CRC, FIFO or overrun error. `tools/eth2test.sh`
runs the speed walk. The Linux side -- the converter driver, the device tree,
and why `S15fpga` routes GEM1's clocks -- is in "The Ethernet PHYs" in
[the Linux guide](linux-guide.md).

⚠ **The core learns the link speed only through its MDIO register.** Its
transmit clock depends on it, and nothing in the RGMII stream sets it. Linux's
`xilinx_gmii2rgmii` writes it after every PHY status read; without that
driver the core stays at its reset speed and only one link rate passes
traffic. Bits `[6:5]` of the status word at `0xF4` show what it was told.

⚠ **The clock-group gate skips virtual clocks.** The core times its RGMII
inputs against a *virtual* copy of the receive clock, so paths from that
virtual clock to `phy2_rxc` are the I/O timing itself, and must stay timed.
`constraint_check.tcl` leaves clocks with no source pin out of the "other
clocks" it requires to be asynchronous.

⚠ In the full design, PHY2's MDIO belongs to GEM1, and EMIO bits 8 and 9 (gpio 62/63)
carry the camera connector's two control lines. The `ddr` design hands
PHY2's MDC and MDIO to Linux on those two lines.

<a id="the-ethernet-mac-core"></a>
<a id="10-the-ethernet-mac-core"></a>
## 10. Standalone Ethernet MAC

`eth_crc32.sv`, `eth_mac_tx.sv` and `eth_mac_rx.sv` are the frame layer of a
MAC for PHY2, the PL-side RTL8211F. Speed-agnostic — one byte per enabled
clock, so the same core serves 1000, 100 and 10 Mb/s and only the clock rate
below it changes.

The CRC is checked against an answer from **outside this design**: CRC-32 of
`"123456789"` is `0xCBF43926`, the published check value for CRC-32/ISO-HDLC.
That matters because a CRC has four conventions to get wrong, and getting any
of them wrong produces something perfectly self-consistent — a transmitter and
receiver sharing the mistake agree with each other forever and are rejected by
every other device on the wire.

⚠ Two frame residues appear in the literature, `0xC704DD7B` and `0xDEBB20E3`.
They are the same number bit-reversed; which one applies depends on whether
the register is kept reflected. This one is not, so it is `0xC704DD7B`.

⚠ Padding is to **60** bytes, not 64. The 64-byte minimum includes the FCS.

<a id="not-in-either-design"></a>
<a id="101-not-in-either-design"></a>
### 10.1 Integration status

This is a frame layer, benched but not wired into a top level. The PL
Ethernet port does not need it: GEM1 is already a complete MAC with a
mainline driver, and reaching it over EMIO costs a protocol converter rather
than a MAC, a DMA engine and a register map a Linux driver would accept.

## 11. I2C

Four I2C buses on this board sit on **PL** pins, and the PS has no I2C
controller wired out to any of them:

| Bus | Pins | Bank | On it |
|---|---|---|---|
| HDMI out | H14 / K15 | 35, 1.8 V | ADV7511 at 0x39 |
| HDMI in | AC24 / AD24 | 11, 3.3 V | ADV7611 at 0x4C |
| Camera + EEPROM | AC19 / AB20 | 9, 3.3 V | AT24C256 at 0x50 |
| FMC | AC21 / W23 | 11, 3.3 V | whatever card is fitted |

`emio_pads.v` puts an `IOBUF` on each pin and hands it to the PS as an EMIO
GPIO, and Linux's `i2c-gpio` bit-bangs them. **No I2C master in the fabric.**
These are 100 kHz configuration buses touched a few dozen times at boot; a
soft master would be more logic, more registers and another thing to debug for
no gain. The first three buses are wired; the FMC's is not.

The PS7's EMIO GPIO is three wires per bit — `GPIO_O`, `GPIO_T` (1 = release)
and `GPIO_I` — which is exactly an `IOBUF`, so that is all the module is.

<a id="the-gpio-numbers-are-fixed-by-the-pl"></a>
<a id="111-the-gpio-numbers-are-fixed-by-the-pl"></a>
### 11.1 GPIO numbering

Linux numbers EMIO GPIO *n* as **54 + n**, and the order the top level wires
them in is what the device tree's `i2c-gpio` nodes name. Change one and the
other has to follow:

| EMIO bit | Linux gpio | Signal |
|---|---|---|
| 0 | 54 | fan tachometer (in) |
| 1 | 55 | `HDMI_TX_SCL` |
| 2 | 56 | `HDMI_TX_SDA` |
| 3 | 57 | `HDMI_RX_SCL` |
| 4 | 58 | `HDMI_RX_SDA` |
| 5 | 59 | `CAM_EE_SCL` |
| 6 | 60 | `CAM_EE_SDA` |
| 7 | 61 | `HDMI_RX_RST` (out) |
| 8 | 62 | full: `CAM_GPIO`, J9 pin 5 -- the camera module's power enable, the sensor's `pwdn-gpios`. `ddr`: `PHY2_MDC` (out) |
| 9 | 63 | full: `CAM_CLK`, J9 pin 4 -- unused by a Pi-style module. `ddr`: `PHY2_MDIO` |
| 10–13 | 64–67 | LED1–4 (out) |
| 14–17 | 68–71 | KEY1–4 (in) |
| 18–51 | 72–105 | the 40-pin header J8 |
| 52–55 | 106–109 | full: SFP1/SFP2 `TX_DISABLE` (read back), SFP1/SFP2 `LOS` |
| 56 | 110 | full: the CSI-2 receiver's video reset (out, read back) |

⚠ **The ADV7611 needs its reset released before it answers at all.**
`HDMI_RX_RST` has a 4.7K pull-down, so the chip sits in reset until the PL
drives that pin high — a device tree gpio-hog does it. Looking for an ADV7611
on the bus before releasing it finds nothing, and the bus is not the problem.

⚠ **Nothing drives an I2C line high.** The device tree marks every one
`GPIO_OPEN_DRAIN`, so gpiolib releases a line by turning the pin into an input
and lets the board's pull-ups pull it up. Two devices driving opposite levels
on a shared line is a short, not a bus.

<a id="ddr--the-pls-own-gigabyte-of-dram"></a>
<a id="12-ddr--the-pls-own-gigabyte-of-dram"></a>
## 12. PL DDR3

The board carries a second 1 GB of DDR3 (2× MT41J256M16, DDR3-1600 grade) on
HP banks 33/34, wired to the PL and invisible to the PS. This design gives it
a MIG controller and maps it where Linux can reach it.

| Window | Slave |
|---|---|
| `0x4000_0000` .. `0x7FFF_FFFF` (M_AXI_GP0) | MIG → PL DDR3, 1 GB |
| `0x8000_0000` .. `0xBFFF_FFFF` (M_AXI_GP1) | `axi4_regs` — the register file (see "Registers" under `board/`) |

The mapping falls out of the hardware: **GP0's window is exactly 1 GB and PS
DDR ends at `0x3FFF_FFFF`**, so the PL DRAM drops in at `0x4000_0000` with no
decode and no hole. That is also why this design puts the registers on GP1 —
they cannot share a window with a slave that fills it.

<a id="what-this-is-not"></a>
<a id="121-what-this-is-not"></a>
### 12.1 PS and PL memory separation

A fast path. M_AXI_GP0 is 32 bits at 100 MHz — about 400 MB/s — so this maps
the DRAM for *correctness*, not bandwidth. The memory is deliberately clocked
at 400 MHz (DDR3-800) rather than its 800 MHz rating for the same reason: the
bus is the limit either way. Raising it is one constant in `gen_mig_prj.py`
plus the two CAS latencies the part's MIG description tabulates against the
period.

Bandwidth needs a PL-side master. BIST engine 2 (see "Engine 2: PL DDR3, from
inside the fabric") sweeps the MIG from the fabric; moving data between PL
DDR3 and PS DDR at speed would need a DMA engine between the MIG and
`S_AXI_HP`, which this design does not have.

<a id="why-migs-pins-come-from-a-generated-file"></a>
<a id="122-why-migs-pins-come-from-a-generated-file"></a>
### 12.2 MIG pin generation

MIG reads its pin assignment from a `.prj` XML, not from an XDC, so the pin
list would otherwise exist twice. `gen_mig_prj.py` builds `../mig.prj`, which
both designs read, from the
DDR3 section of `../RK_ZYNQ7100_master.xdc` — the list derived from the
schematic and checked pin by pin against the Vivado package — and refuses to
write anything if it does not parse exactly 71 pins. The generated file is
committed so a clone builds without Python.

Three board facts are set in the script rather than read from the XDC, because
they are not in it:

- **VREF is external.** Bank 33's VREF pins are tied to the board's VTTREF, so
  `InternalVref` is 0. Getting this wrong gives a design that builds and then
  fails to calibrate.
- DCI is used on both banks — VRP/VRN reference resistors are fitted.
- The parts are `MT41J256M16XX-125`, which MIG already knows
  (`data/mem_tlib/ddr3_sdram/components/`), so the timing comes from Xilinx's
  own part description rather than from the datasheet by hand.

<a id="why-two-converters-instead-of-an-axi-interconnect"></a>
<a id="123-why-two-converters-instead-of-an-axi-interconnect"></a>
### 12.3 AXI conversion

GP0 is AXI3 at `fclk_clk0`; the MIG slave is AXI4 at `ui_clk`. The MIG is
GP0's only slave, so there is nothing to decode, and the one arbitration there
is -- the CPU or BIST engine 2 -- is `axi_owner`'s. So the path is an
`axi_protocol_converter` (AXI3→AXI4), `axi_owner`, then an
`axi_clock_converter`, each saying plainly what it converts, where an
interconnect would hide all three behind a crossbar and widen the ID the MIG
was generated for.

<a id="why-the-registers-stay-on-the-ps-clock"></a>
<a id="124-why-the-registers-stay-on-the-ps-clock"></a>
### 12.4 Register clock domain

`ui_clk` only exists once the MIG's MMCM locks. If it never does, anything on
that clock hangs the CPU forever on its first access, and the only symptom is
a dead board. The register block runs on `fclk_clk0`, which the PS PLL
provides regardless, so it can still be read and still reports `mmcm_locked`
and `init_calib_complete` — the difference between a diagnosis and a power
cycle. `STATUS` (GP1 + `0x14`) carries both:

| Bit | Meaning |
|---|---|
| 0 | `init_calib_complete` — DDR3 calibrated |
| 1 | `mmcm_locked` |

Bit 0 also drives the bicolor LED8: **solid when the DRAM calibrated, blinking
when it did not**, with nothing running on the CPU.

<a id="testing-it-from-linux"></a>
<a id="125-testing-it-from-linux"></a>
### 12.5 Linux test procedure

The PL DRAM is deliberately *not* given to the kernel as system memory — it is
far slower than PS DDR and mixing it into the allocator would make every
allocation a lottery. It is reached through `/dev/mem`, which maps it because
it is outside the kernel's RAM map:

```
devmem 0x80000014 32     # STATUS: expect 0x3 (calibrated + MMCM locked)
sh test-ddr.sh           # registers, then memtest (-b 0x80100000 under the board design)
```

⚠ **`dd if=/dev/mem bs=1M skip=1024` does not work on this memory.** It fails
with `Bad address` and moves zero records: `/dev/mem`'s read()/write() path
goes through `xlate_dev_mem_ptr()`, which returns NULL for a physical address
that is not kernel RAM, so the copy gets `-EFAULT`. `mmap()` of the same range
is fine — which is why busybox `devmem` reads and writes it happily. Anything
bulk has to mmap, hence `memtest.c`:

```
arm-buildroot-linux-gnueabihf-gcc -O2 -static -o memtest memtest.c
```

It runs four tests, cheapest and most diagnostic first. The **address bus**
test matters most: it writes one marker per address bit and reads them all
back only after every write, because a stuck or swapped address line makes two
addresses the same cell — which a pattern test over one region cannot see at
all, since the aliased write lands on top and the read still matches. Then a
data-bus test of walking ones and zeros that names the offending DQ line, a
whole-device pass of one word per 4 KiB page across the gigabyte, and a timed
bulk block at each end.

<a id="measured-on-the-hardware-1"></a>
<a id="126-measured-on-the-hardware"></a>
### 12.6 Hardware validation

`test-ddr.sh` on the board:

```
STATUS 0x00000003                     init_calib_complete + mmcm_locked
== address bus     29 addresses (offset 0 and each power of two to 0x20000000)
== data bus        walking ones and zeros, 32 bits
== whole device    262144 words over 1024 MiB, 1.4 s
== bulk 8 MiB at the bottom (0x40000000)
   write 11.9 MB/s, read+verify 7.0 MB/s (uncached)
== bulk 8 MiB at the top (0x7e000000)
   write 11.9 MB/s, read+verify 7.0 MB/s (uncached)
PASSED: 0 mismatches
```

Build: WNS **+0.905 ns**, WHS +0.056 ns, no critical warnings.

**About those MB/s.** They are not the DRAM and not the ~400 MB/s the GP0 bus
could carry. `/dev/mem` maps non-RAM as uncached device memory, so every
32-bit access is a full round trip — CPU, protocol converter, clock crossing,
MIG, DRAM and back — with no cache and no burst to amortize it. The figure is
latency-bound, and it is the honest floor for word-at-a-time access. Getting
near the bus ceiling needs bursts, which means a DMA engine rather than the
CPU; getting past the ceiling needs a PL-side master (see above).

## 13. Board registers

`board/` carries everything: the PL DDR3, the register file and every
peripheral on the PL's pins (see the table at the top). Its ID, scratch and
counter registers prove the whole PL path end to end: Vivado build →
bitstream format → `fpga_manager` → FCLK → M_AXI_GP1 → PL I/O banks.

<a id="the-address-map"></a>
<a id="131-the-address-map"></a>
### 13.1 Address map

The PS gives the fabric two 1 GB master windows and the PL DRAM is exactly
1 GB, so the DRAM takes all of GP0 and everything else hangs off GP1 through
one crossbar:

| Address | What |
|---|---|
| `0x4000_0000`–`0x7FFF_FFFF` (M_AXI_GP0) | the PL DDR3, through the MIG |
| `0x8000_0000` (M_AXI_GP1) | the HDMI capture VDMA |
| `0x8001_0000` | the camera VDMA |
| `0x8002_0000` | the CSI-2 receiver, 128 KB (its D-PHY registers sit above the controller's) |
| `0x8010_0000` | the register file |

⚠ The register file is an AXI3 slave on an AXI4-Lite crossbar port. The
protocol converter ahead of the crossbar splits a CPU burst into single
beats, so the file answers a `memcpy` the same way it answers `devmem`; it
never sees a burst. Read responses hold their data and metadata while
RREADY is low, including live counter/status values and sub-block read data.
Core writes honor byte strobes; sub-block control writes require full words.

<a id="registers-1"></a>
### 13.2 Registers

directly on GP1 with no crossbar in front and therefore still takes bursts.

<a id="led14-and-the-keys-belong-to-linux"></a>
<a id="133-led14-and-the-keys-belong-to-linux"></a>
### 13.3 Linux LEDs and keys

They are EMIO GPIOs rather than register bits, so Linux drives them with
`gpio-leds` and reads them with `gpio-keys` — an LED class and an input
device, not something only `devmem` can reach. The keys are also readable at
`0x0C`, because fanning an input out costs nothing and keeps the
register file useful with no operating system at all.

An LED pin is always an output, so those four take `GPIO_O` straight with no
`IOBUF` and no tristate; the same bits are fed back into `GPIO_I` so reading
the GPIO returns what was written.

### 13.4 Hardware validation

```
devmem 0x80100000 32            -> 0x5A710002   ID
devmem 0x80100010 32 (twice)    -> two different values, the counter running
devmem 0x80100004 32 0xDEADBEEF -> reads back 0xDEADBEEF, the scratch register
devmem 0x80100014 32            -> 0x00000007   DDR3 calibrated, both MMCMs locked
```

can drive them through `gpio-leds`; those bits are stored and read back and

<a id="why-hand-written-rtl-instead-of-axi-gpio"></a>
<a id="135-why-hand-written-rtl-instead-of-axi-gpio"></a>
### 13.5 Register implementation

`axi4_regs.v` is about 200 lines of logic and has no IP to configure, so when a read
returns the wrong value the cause is in one readable file. It is a real **AXI3**
slave, not AXI4-Lite: in `ddr/` it sits directly on M_AXI_GP1, a full AXI3
master, and the CPU does issue bursts (a cache-line fill through `/dev/mem`, a
`memcpy`), so `AWLEN`/`ARLEN` are honored and `RLAST` lands on the right beat.
An AXI-Lite slave wired straight to a GP port looks fine under `devmem` and
then hangs the bus on the first burst. In `board/` the protocol converter
ahead of the crossbar splits bursts first.

<a id="two-traps"></a>
<a id="136-two-traps"></a>
### 13.6 Integration constraints

- **PS7 property overrides must not be re-applied from the shared list.**
  `build.tcl` applies `ps7_config.tcl` and then sets the ports this design
  actually uses. Applying the overrides and *then* running the
  verify-and-retry pass over the full shared list puts the shared values
  straight back — a few hundred `BlackBox module ps7 has unconnected pin
  S_AXI_HP1_*` critical warnings. `build.tcl` removes the overrides from the
  list before applying and verifying it.
- **Apply the PS7 settings in one `set_property -dict` call.** Applied one at a
  time, the IP validates each against the state so far and refuses the 1.8 V
  MIO settings because bank 501 has not moved off its 3.3 V default yet.
  `../linux/gen_ps7.tcl` applies them in one call for this reason.

<a id="why-the-register-file-stays-on-devmem"></a>
<a id="137-why-the-register-file-stays-on-devmem"></a>
### 13.7 Software access

The register file is reached with `devmem`, deliberately: it needs
no kernel rebuild to iterate on, and every block behind it that *deserves* a
driver has one. LED1-4 are `gpio-leds`, the keys are `gpio-keys`, the BIST
engines have `generic-uio` nodes for their interrupts, the fan is `pwm-fan`
under hwmon, and the HDMI input and the camera are V4L2 devices. What is left
in the register window is diagnostics -- frequency counts, capture geometry, link status --
which is exactly what `devmem` is good for.
